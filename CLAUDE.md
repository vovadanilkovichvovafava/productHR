# productHR — HR-продукт (подбор, «Штат», кадры)

Отдельный продукт, выделенный из внутренней платформы Энцеладус
(`alex4udak-blip/HR-bot-`) 27.10.2026, с прицелом на выход на рынок. MST —
первый клиент. Репозиторий **приватный**: в комментариях к правкам и ниже в
этом файле встречаются реальные имена людей и разборы случаев с прода.

## Откуда взялось и что вырезано
Исходная точка — снимок Энцеладуса `73d690a` (коммит `import:` в начале
истории), без истории Энцеладуса. Дальше — вырезы, по одному коммиту на раздел,
чтобы любой возвращался одним `git revert`:
- `cut(практика)` — Практика: практиканты, их чаты, созвоны, критерии чатов,
  выгрузка из Prometheus. Решение владельца 27.10.2026: Практика остаётся в
  Энцеладусе.
- `cut(энцеладус)` — проекты и задачи, «Команда» (загрузка по проектам),
  блокеры, интеграция с Saturn, MCP-токены для задач, автозадачи из чатов,
  итог дня и стендапы в боте, вкладка «Задачи» в мини-аппе, внутренние отчёты
  и заметки репозитория.

Что в продукте: HR (кандидаты, воронки, «Штат», заявки, анкеты, аналитика,
ПЭН, импорт, выгрузки, корзина, журнал), «Управление»/кадры — модуль под
`frontend/src/factorial` (сотрудники, отпуска, документы, кабинет), админка
(пользователи, роли, отделы, настройки), расширение hh.ru, мини-апп (доступы,
события), Telegram-бот для HR-уведомлений и привязки аккаунта.

Сознательно ОСТАВЛЕНО на следующий шаг:
- **модели и таблицы всех разделов** (`models/database.py`): схема базы
  совпадает с Энцеладусом, поэтому перенос данных MST — обычный снимок без
  преобразований. Таблицы вырезанных разделов просто останутся пустыми;
- **внутренности `bot.py`**: обработчики автозадач и вечерних отчётов на
  месте, но фоновые задачи сняты, а в продукте нет чатов с включёнными
  автозадачами — код не срабатывает. Вычистить отдельным проходом;
- сервисы, на которые опирается живой код (разбор звонков, участники чатов,
  транскрибация, `external_links` для парсера резюме);
- обёртки API во фронте `chats.ts`/`calls.ts`: в них же критерии и курсы
  валют, которыми пользуются HR-экраны;
- название модуля **Factorial** в коде (~110 файлов). Это чужая торговая
  марка — для продукта на рынке переименовать.

### «Наблюдатель» (`OrgMember.is_readonly`) — смотреть можно всё, трогать нельзя
Ментор (Егор, Влад — 01.10.2026: «Ты должен видеть кандидатов, но просто не
исправлять»). Флаг обычно висит поверх прав админа, поэтому «само» ничего не
отключается — каждое место закрывают явно:
- **Сервер** — одна точка `get_current_user` → `observer_check_needed(method, path)`
  в `services/auth.py`: любой не-GET вне белого списка даёт 403. Белый список
  (`OBSERVER_WRITABLE_PREFIXES`) — это СВОЙ домен наблюдателя: auth, Практика
  (чаты/созвоны/практиканты/критерии), проекты, отпуска, блокеры, свои
  уведомления; практик-лид с этим флагом работает там как обычно.
- **Клиент** — тот же список в `services/api/client.ts`
  (`OBSERVER_WRITABLE_PREFIXES`, `isObserverBlocked`, включается из `authStore`).
  Изменяющий запрос не уходит вовсе, человек видит одно сообщение. Раньше 403
  гасили молча, и выглядело это как «кнопка сломалась»: комментарий «отправлен»,
  этап «сменился» и вернулся после F5. **Правите список — правьте оба.**
- **Интерфейс** — кнопок записи у наблюдателя нет: «+» в HR-сайдбаре, создание и
  правка вакансий/заявок, «Взять в работу»/«Отказаться», массовая плашка,
  «Поделиться» (она СОЗДАЁТ публичную ссылку), метки, реакции, чипы «Файл»/
  «Анкета» (окно СОЗДАНИЯ анкеты), меню записи в ленте. Форма вакансии
  открывается в режиме просмотра (`isReadOnlyRequest`).
- **Что он при этом видит — ВСЁ.** Лента карточки (переходы + комментарии),
  фильтр «Действия», файлы со скачиванием, ответы кандидата во вкладке «Анкета»,
  чужие воронки, аналитика.
- Грабли, из-за которых чинили: в `CandidateVacancyCard` один флаг `readonly`
  означал и «нельзя нажимать», и «это снапшот влитого дубля, истории у него
  нет» — наблюдателю карточка открывалась с ПУСТОЙ лентой. Теперь снапшот —
  отдельный проп `snapshot`, а `readonly` только убирает кнопки.
- Не закрыто: страница «Статусы» (её в тот момент переписывала соседняя вкладка)
  и страницы настроек HR — там кнопки ещё выглядят активными, но запись режется
  клиентским стражем с сообщением. Довести до вида «кнопок нет» — отдельной
  задачей.

### Скоуп по воронкам: «вижу только свою воронку»
Продолжение истории (01.10.2026, Мария): «давать доступ полностью ко всей базе не
нужно, мы им нанимаем в трафик — значит доступ только к трафику». До этого
кандидаты были ОБЩИМИ для организации, сужения не было вовсе.

- Хранится в `org_members.scope_vacancy_ids` (JSON, список id вакансий).
  **Пусто/NULL — ограничения НЕТ** (поведение всех существующих людей не
  изменилось); непустой список — видны только кандидаты с заявкой в этих
  воронках и сами эти воронки. Суперадмина скоуп не касается.
- Ставится галочками: Настройки → Пользователи → карточка человека, блок «Какие
  воронки видит» (виден, когда роль «Наблюдатель»). Эндпоинты:
  `PATCH /users/{id}` (суперадмин) и `PATCH /organizations/current/members/{id}/role`
  (админ орга); чужие вакансии из списка отсекаются по org_id.
- Вся логика — `services/vacancy_scope.py`. Проверки стоят в ДВУХ горлышках, а не
  по эндпоинтам: `check_entity_access` (любой доступ к карточке) и фильтр в
  запросах списков (`_base_candidate_query`, `/entities`, список вакансий).
  Ручки вакансий и заявок (`/vacancies/{vacancy_id}/…`,
  `/vacancies/applications/{application_id}/…`) проверяет одно горлышко —
  `check_vacancy_access` (`_ensure_path_in_scope`): до 20.10.2026 скоуп стоял
  только на чтении, и человек со скоупом, которого сделали рекрутёром (скоуп
  при смене роли остаётся), мог по id двигать и удалять заявки чужих воронок.
  Плюс `ensure_vacancy_visible` на ручках вакансии и `ensure_entity_visible` на
  «мелких» ручках кандидата (метки, анкеты, история писем, рекомендации,
  staff-status, сквозная история этапов) — они достают данные по entity_id мимо
  check_entity_access, и без этой строчки чужой кандидат утекал по кусочкам
  (нашлось при аудите: 7 ручек отдавали 200).
- Чужая воронка/кандидат отвечают **404, а не 403**: сам факт существования —
  тоже информация, а id перебираются. То же для вакансий и заявок ДРУГОЙ
  организации (с 24.10.2026, `_ensure_path_in_org` в `check_vacancy_access`;
  наблюдатель своей организации не затронут). Сторож — `tests/test_vacancy_other_org_404.py`.
- Кандидат в двух воронках, одна из которых разрешена: сам он виден, но блок
  чужой воронки в карточке скрыт (`/entities/{id}/activity` фильтрует заявки).
- Баннер наблюдателя (`components/app/ObserverBanner.tsx`) при непустом скоупе
  пишет «вам открыты отдельные воронки» — «вы видите всё» было бы неправдой.
  Вид (владелец, 21.10.2026): жёлтый, текст по центру, но КАРТОЧКОЙ на линиях
  страницы (как полоса этапов), а не полосой во всю ширину — та прилипала к
  сайдбару и уходила за правый край.
- Наблюдатель — это сторонний отдел (владелец, 21.10.2026): своих воронок нет,
  заходят найти и посмотреть кандидата. Скоуп по воронкам по умолчанию пуст;
  на проде он стоял только у тестового «Рекрутер тест» (Трафик). В воронке у
  наблюдателя и суперадмина «Все рекрутёры» — исходный вид, без крестика.
- НЕ ограничены намеренно (решение владельца 01.10.2026): «Статусы» (дашборд
  практики/отделов — Мария назвала его открытой информацией), «Аналитика»,
  «Заявки», «Анкеты». Если потребуется — скоупить там же, через
  `get_scope_vacancy_ids`.
- Проверялось на локальной копии прод-воронки «Трафик» (635 заявок, то же
  распределение по этапам и рекрутёрам; имена синтетические — персональные
  данные с прода не выгружались). Скрипт: `seed_scope_test.py` в scratchpad
  сессии, с ключом `--clean`.

## Модель работы HR
- **Кандидаты общие** для организации: смотреть и править может любой рекрутёр,
  неважно, кто добавил (`check_entity_access`, уровень edit). Удаление и передача
  — у автора и админов.
- **Воронка** = вакансия. Заявка (`VacancyApplication`) — связка кандидат↔вакансия,
  у неё свой этап. Заявку «берут в работу» лично (`extra_data.accepted_by`), в
  одной воронке может работать несколько рекрутёров (со-рекрутёры,
  `ApplicationCoRecruiter`). Кандидат может быть в нескольких воронках сразу —
  это норма.
- **«Забрать»** — два случая (владелец, 20.10.2026):
  - кандидата в выбранной воронке НЕТ — он добавляется туда на того, кто
    забрал, и всегда на этап «Новый» (новый подбор). В прежней воронке он
    остаётся у прежнего рекрутёра как был — один кандидат в двух воронках;
  - кандидат УЖЕ в этой воронке — ПЕРЕНОС (для кандидатов уходящих
    рекрутёров): владелец заявки меняется на нового, прежний кандидата теряет;
    карточка («кто добавил») переходит тоже, если была за прежним.
  Со 28.08 по 21.09 второй случай дописывал к заявке второго рекрутёра
  (со-рекрутёр); на проде таких пар 0 (проверено 20.10.2026), код их
  поддерживает на случай старых данных. Массовая передача всех воронок уходящего —
  отдельный механизм, `services/recruiter_transfer.py` (см. «Передача дел» ниже).
  **С 26.10.2026 окно «Забрать» заранее говорит, что произойдёт** («Кандидат
  появится в этой воронке на этапе „Новый“» / «Сейчас в этой воронке кандидата
  ведёт Пётр, этап … Вести его будете вы… Пётр получит уведомление» / «уже
  ведёт»), данные — `owner_id/owner_name` в `/entities/{id}/activity`. Перенос
  пишет в ленту запись «Сменился рекрутёр: теперь X, раньше Y» (этап тот же,
  её корзина ничего не двигает) и шлёт уведомления прежнему и новому; ответ
  несёт `take_outcome` (added/transferred/unchanged). Сервер проверяет:
  получатель — рекрутёр/админ, не наблюдатель (`valid_handover_recipients`),
  и сам видит воронку (`can_access_vacancy` + его скоуп); кандидат виден тому,
  кто нажал (`ensure_entity_visible`; то же в «Добавить в воронку»). Вопрос
  «Был отказ» — только когда кандидат заново попадает в воронку. Получатели —
  `assignable-users?include_owners=true` (Настя тоже). Имена в текстах —
  только именительный падеж: склонять их мы не умеем.
- **Чей кандидат в воронке** = автор заявки (`created_by`), а если он пустой
  (старые данные, удалённый пользователь — FK `SET NULL`) — владелец вакансии.
  Одно правило и для метки «HR: …» (`services/hr_tags.py`), и для воронки со
  скоупом по рекрутёру (`recruiter_owns_application` в `vacancies/common.py`).
  Разъедутся — метка скажет «кандидат Марии», а в воронке Марии его не будет.
- **«Мои вакансии»** в сайдбаре = где ты лично принял. Выпадающий список там
  («Выбрать владельца вакансий») кладёт в адрес `?recruiter=<id>` — страница
  воронок показывает кандидатов этого человека. Работает для всех ролей.
- **Чьих кандидатов видно в воронке — фильтр «Рекрутёр: …»** над списком, на
  любом этапе (`components/funnels/FunnelRecruiterFilter.tsx`; логика —
  `useFunnelCandidates`). Владелец, 21.10.2026, после жалобы Марии «шарим
  вакансию на двоих-троих, очень много доп действий»:
  - по умолчанию каждый видит СВОИХ (кого добавил сам) — чужие сами «не
    прилетают»; выбран рекрутёр в сайдбаре (`?recruiter=`) — его; суперадмин,

- **Кандидат ВНЕ воронок двигается по этапам так же.** Заявки у него нет, писать
  `StageTransition` некуда, поэтому запись о переводе живёт комментарием
  (`extra_data.notes`, поля `stage` + `from_status`). Такая запись создаётся при
  КАЖДОМ переводе, даже без комментария (тогда у неё пустой текст и в ленте
  видна одна строка со статусом) — иначе этап менялся молча и следа не
  оставалось. Обычный комментарий без текста по-прежнему не сохраняется. Удаление такой записи
  возвращает кандидата на прежний статус — как корзина у записи истории в
  воронке (маркер `NOTE_STAGE_UNDO`; требование владельца 28.09.2026: «неважно,
  воронка это или нет»). Откат срабатывает, только если запись описывает
  ТЕКУЩИЙ статус.
- **История этапов** (`StageTransition`): удаление ПОСЛЕДНЕЙ записи = отмена
  перевода — заявка возвращается на её `from_stage` (и общий статус кандидата
  пересчитывается), маркер `HISTORY_UNDO`. Старые записи выше по ленте —
  просто чистка лога, этап не трогаем (`HISTORY_DELETE`). Откат срабатывает
  только если `to_stage` записи совпадает с текущим этапом: этап уже подвинули
  руками — значит, запись его больше не описывает.
- **Окно «Сменить этап подбора»** (как в Huntflow, 23.09.2026): при открытии уже
  помечен СЛЕДУЮЩИЙ этап (`nextStageStatus` в `candidateDetail/model.ts`; отказ,
  резерв и архив сами не подставляются). Выбран этап, на котором кандидат уже
  стоит, — вместо поля комментария серая плашка «Кандидат сейчас находится на
  этом этапе подбора», «Сохранить» недоступно. После перевода карточка остаётся
  открытой, этап меняется на месте: ни тоста, ни перезагрузки, в воронке
  перемещённый кандидат закреплён в текущей вкладке, пока рекрутёр сам с неё не
  уйдёт (раньше он пропадал из списка и справа открывался следующий).
- **Окно смены этапа не предлагает того, чего заявке поставить нельзя.** Пикер
  на «Все кандидаты» строится из колонок доски через `buildStagePickerOptions`,
  и служебная «Вне воронки» (`BOARD_OTHER_STATUS`) из него ВЫРЕЗАНА: у заявки
  такого этапа нет, сохранение не слало на сервер ничего, а карточку на доске
  двигало — «перевёл, а он на месте» (Гром Виктор, 24.09.2026). Если статус без
  пары среди этапов заявки всё же попадёт в окно, `cardChangeStage` показывает
  ошибку и НЕ двигает карточку: молчаливых переводов быть не должно.
- **Кандидат в нескольких воронках.** У каждой воронки свой этап и своя карточка
  в стеке; общий статус (колонка «Все кандидаты») сервер считает по «актуальной»
  заявке — самой свежей ЖИВОЙ, отказ/резерв учитываются, только когда живых не
  осталось. Поэтому отказ в ОДНОЙ воронке не уводит кандидата в колонку «Отказ»,
  пока он работается в другой. Фронт ставит карточку в колонку по полю
  `entity_status`, которое возвращают `PUT /vacancies/applications/{id}` и
  удаление записи истории, — не по выбранному этапу: иначе до F5 список
  расходился с сервером.

### «Был отказ» — повторные кандидаты (22.10.2026)
Владелец: «тех, кто пытается повторно пройти собеседование, хотя уже получил
отказ». Матчер дублей сравнивает только личные данные и про отказ не знал; на
проде все 6 пар «одна карточка в Отказе, другая живая» были помечены дублями, и
ни одну не разобрали — плашка говорила «Возможно тот же человек · 64%» без слова
об отказе. Решение владельца: **предупреждать, не запрещать**; отказы — и в
Enceladus, и в архиве ClickUp.
- Ядро — `services/prior_rejection.py`. Отказ = заявка на этапе «Отказ» в
  неудалённой воронке (дата, воронка, кто — из `StageTransition`, с какого этапа,
  комментарий, `rejection_reason`), запись ленты `stage=rejected` (вне воронок),
  прохождение ClickUp со статусом «…: нет» (`kind=rejected`) или «неявка» /
  «не отвечают» (`kind=no_show`). Чей: связанных карточек того же человека
  (`hidden_duplicate_id` в обе стороны) и, где просят, свои ДРУГИЕ воронки.
- Где видно: строка «Все кандидаты» (`KanbanCard.prior_rejection`, кроме
  вкладки «Отказ»; свои воронки не берём — их этапы и так в строке) и воронки
  (`ApplicationResponse.prior_rejection`, плюс отказы в других воронках);
  плашка в карточке — ОДНА с плашкой дубля (`CandidateAlertCard`: мягкая
  карточка «Уже был у нас — отказ … · воронка · рекрутёр», ниже комментарий и
  «точный дубль: имя + телефон», кнопка «Сравнить»; владелец 22.10.2026 —
  прежние две плашки и красная полоса во всю ширину занимали полэкрана;
  данные — `useVisiblePriorRejections`, `GET /entities/{id}/prior-rejections`); вопрос «Всё равно добавить?» в «Взять на
  вакансию», «Забрать» и «Добавить в вакансию» в воронке
  (`usePriorRejectionGate`; при массовом добавлении не спрашиваем); расширение —
  красный блок до «Добавить» (`check-duplicate` → `prior_rejection`). Всё на
  фронте — `components/candidates/priorRejection.tsx`.
- Окно сравнения показывает отказы каждой анкеты (раньше «отклонён {дата}» читал
  `timeline_events`, которого не пишет никто, — не показывался никогда).
- **До создания карточки** окна «Новый кандидат» и «Загрузка из файла» спрашивают

Сторож — `tests/test_prior_rejection.py`, `__tests__/priorRejection.test.ts`.

## Аватарки и кэш файлов (16.10.2026)
Аватарка в списке «Все кандидаты» — полноразмерное фото (~340 КБ, у 766 из 1080

immutable`): байты файла по id не меняются никогда. JSON, PDF и не-200 — по-

`background.js`, парсеры `content/*.js`), сервер — `routes/magic_button.py`.
**Расширение само НЕ обновляется**: его ставят из zip (страница `/extension`,

- правки на СЕРВЕРЕ доходят до всех сразу, правки в попапе/парсерах — только до

## Новые колонки в базе (правило после аварии 28.09.2026)
Миграции Alembic в репозитории поломаны, колонки заводятся «страховками». Класть
новую колонку в ХВОСТ общего ensure-блока `start.sh` НЕЛЬЗЯ: этот блок — один
python-скрипт на 800 строк, первая же ошибка внутри обрывает его целиком, а
снаружи стоит `|| echo`, поэтому провал выглядит в логе как успех. Так 28.09
уехал код с `vacancy_applications.pinned_entry_key` без самой колонки: SQLAlchemy
перечисляет ВСЕ поля модели в каждом SELECT, поэтому падали любые запросы к
заявкам — у рекрутёров не открывалась карточка и не двигались кандидаты.

Как правильно:
1. колонку — в `init_database()` (`api/db/init.py`, шаг 3.0), каждую своей
   `run_migration`: падение соседней не мешает;
2. проверять локально ТЕМ ЖЕ путём, каким она поедет на прод: снести колонку
   (`ALTER TABLE … DROP COLUMN`) и поднять бэкенд заново, а не создавать её
   руками через psql;
3. после деплоя дёрнуть то, что её читает (карточка кандидата, воронка), а не
   только проверить, что фронт новый.

При старте приложение сверяет модели с базой и пишет `SCHEMA_DRIFT` — «в базе
нет колонок: …». Если такая строка есть в логе деплоя, раздел уже сломан: надо
заводить колонку, а не ждать жалоб.

## Логи и диагностика
В бэкенде есть маркеры, по ним удобно искать в логах Saturn:
- `STAGE_CHANGE` — смена этапа: кто, заявка, кандидат, воронка, из→в, `via=` путь
  (application / bulk_move / candidate_status / out_of_funnel / entity_edit /
  entity_status / staff_board);
- `STAGE_GUARD mismatch` — фронт просил сменить этап не тому кандидату (409);
- `HISTORY_DELETE` — удаление записи истории (без смены этапа);
- `HISTORY_UNDO` — удалена последняя запись → заявка вернулась на прежний этап;
- `NOTE_STAGE_UNDO` — удалена запись о переводе у кандидата вне воронок → статус вернулся;
- `HISTORY_EDIT` — поправили комментарий к переводу; `ENTRY_PIN` — закрепили/открепили запись ленты;
- `TAKE_TRANSFER` — «Забрать»: заявка, кандидат, воронка, от кого → кому, кто нажал.
- `HANDOVER` — передача дел уходящего: от кого, кто нажал, сколько кому, сколько воронок слито.
- `APPLICATION_DELETE` / `APPLICATION_RESTORE` — «Удалить с воронки» (в корзину) и возврат.
- `AUDIT write failed` — строка журнала действий не записалась (действие при этом прошло).
- `AI_USAGE` — каждый вызов Claude: модель, откуда, токены, примерная цена, ошибка
  (сводка — страница «Расход ИИ»).
- Каждая строка `api.request` подписана тем, кто сделал запрос: `… 200 · Имя (id)`;
  полная история действий — таблица `audit_events` / страница «Журнал действий».
- `RATE_LIMIT` — сработал лимит частоты: метод, путь, адрес, какой лимит (ответ 429).
- `PUBLIC_FORM_CLIENT_ERROR` — у кандидата не отправилась публичная анкета (отчёт браузера: тип, текст, браузер).
- `VACANCY_MERGE` — слияние вакансии-дубля: откуда → куда, сколько переехало и пересеклось.
- `SCHEMA_DRIFT` — при старте: колонки моделей, которых нет в базе (пусто = всё сошлось).
- `KEEP_DEPARTED` — пересчёт статуса не тронул уволенного: его заявка не двигалась;
  `BOARD_STAGE_SYNC` — разовый шаг 20.10.2026: заявки выровнены за доской «Штат».
- `DUP_DIFFERENT` — «Разные люди» по паре кандидатов; `DUP_DECISIONS merge` — перенос
  этих решений при объединении; `DUP_RECHECK` — пересчёт совпадений после правки карточки.

В консоли браузера смена этапа печатает `[stage] PUT application … → этап`.

## Правила работы в этом репозитории
- Репозиторий — весь продукт: HR, кадры («Управление»), админка. Разделов
  Энцеладуса (проекты, Практика, Saturn) здесь нет и не возвращаем без решения
  владельца.
- Сначала проверяешь локально сам (тесты + браузер), потом отдаёшь на ручную
  проверку. Тестовые данные в локальной базе после проверки убираешь.
- В панели хостинга — только чтение. Любое изменение переменных, деплой,
  перезапуск — после явного «да» от владельца.
- Никогда не запускать `docker system prune --volumes` / `docker volume prune`
  на сервере: снесёт том PostgreSQL.
